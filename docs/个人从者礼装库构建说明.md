# 个人从者与礼装库构建

任务“构建个人从者礼装库”用于扫描玩家当前账号的仓库，为后续自动编队建立可复用的本地持有数据。

## 使用方式

1. 在主界面启动任务。任务会依次点击“菜单 → 编成 → 英灵一览”，进入灵基一览仓库。
2. 在“构建范围”中选择“从者和礼装”“仅从者”或“仅礼装”。
3. 在“礼装识别范围”中选择“全部 4/5 星礼装”或“仅羁绊礼装”。仅构建从者时该选项不会生效。
4. 扫描期间不要手动滚动或点击游戏画面。

任务只会切换灵基一览中的从者/概念礼装页、设置筛选并滚动，不会选择卡片、保存队伍或开始关卡。完成后会关闭灵基一览与编成菜单，返回主界面。

## 输出文件

- `config/Inventory/player_servants.json`
- `config/Inventory/player_equips.json`

`config` 是本地配置目录，默认不会提交到 Git。写入采用临时文件加原子替换：只有识别流程确认到达列表底部后，才会替换该类别已有的有效 JSON；中止、超时或识别失败会保留旧文件。

每份 JSON 都包含：

- 数据结构版本、生成时间和实际识别数量；
- 项目内目录总数、已有识图模板数、缺失模板的 ID；
- 每个持有对象的 ID、名称、星级、匹配模板和置信度；
- 从者的职阶与羁绊标签，或礼装的羁绊效果与筛选标签。

礼装图片无法可靠判断是否满破，因此当前版本明确写入 `limit_break: null` 和 `limit_break_known: false`，不会猜测满破状态。

## 完整性的含义

`scan_complete` 表示滚动过程已确认到达当前筛选列表底部。`catalog_complete` 表示工程目录中的每一条数据都有可用于仓库识别的图片模板。两者相互独立；例如扫描可以完整结束，但新礼装尚未补图时，`catalog_complete` 仍为 `false`，对应 ID 会列在 `missing_template_ids` 中。

从者和礼装都会先执行一次“打开筛选 → 重置 → 决定”，以清除游戏原有的默认筛选，然后第二次打开各自独立的筛选页设置本任务条件。从者会在 `[108,28,433,617]` 区域内一边小幅下滑一边匹配“从者”选项，排除经验值卡、芙芙等非从者项目。礼装全部模式会选择 4/5 星；仅羁绊模式会把礼装筛选页滑到底，识别“羁绊效果”文字并点击其左侧复选框。识别采用两帧一致性、最低置信度和第一/第二候选分差三重约束。可见但不能可靠匹配的卡片只计入扫描统计，不会写入玩家库。

## 当前验证状态

- 2026-09-05 已在 1280×720 模拟器上从主界面完成端到端验证。入口“菜单 → 编成 → 灵基一览”、两个仓库页签切换和完成后返回主界面均正常。
- 从者筛选先“重置 → 决定”，再次打开后在 `[108,28,433,617]` 内每次小幅下滑 90px；第 12 次画面命中“变还_从者未选中”，分数为 0.9955。完整扫描在第 55 屏由滚动条连续稳定 3 次确认到底，写入 370 名唯一从者。
- 礼装全部模式的“重置 → 决定 → 再次筛选 5 星/4 星”已完整通过。扫描固定读取 `EquipFaces/list`，不使用 `team`；快速特征只负责筛出唯一候选，最终入库必须由完整 147×56 原图在卡面邻域直接匹配通过。完整扫描在第 126 屏确认到底，写入 406 种唯一礼装，直接匹配分数为 0.8863–0.9937。
- 2026-09-05 对仅羁绊模式进行了完整实机扫描：重置与首次决定命中 0.9710/0.9949，“羁绊效果”命中 0.9975，筛选决定命中 0.9949。顶部和底部交叉截图确认游戏实际筛出 4 行、每行 6 张，共 24 种不同卡面。
- 该测试发现旧扫描器用 `feature_y >= 345` 排除了顶部完整行，修正为从 `feature_y >= 160` 开始识别后，成功归档由 14 种提高到 16 种。其余 8 种在现有 `EquipFaces/list` 中没有可通过完整原图复核的模板（最佳候选约 0.35–0.69，远低于 0.88），因此没有通过降低阈值强行写入。当前 `player_equips.json` 保存的是这次仅羁绊扫描的 16 种可靠结果。
- 发生超时或识别错误时，先通过 MaaMCP 保留并检查错误瞬间截图，再执行返回或恢复流程。礼装横坐标错误就是按此方式从现场截图定位，避免问题画面被返回主界面覆盖。

## 待继续验证

- 补齐上述 8 种礼装的 `EquipFaces/list` 模板后，重跑仅羁绊模式，目标是游戏筛选 24 种、JSON 可靠归档 24 种且无重复 ID。
- 因礼装识别纵向范围已扩展，需要重跑一次“全部 4/5 星礼装”完整扫描；旧的 406 种结果没有覆盖列表复位时的顶部第一行，不能再作为新版本的最终基准。
- 用一个仅有一屏结果的筛选条件验证 `bottom_detection=content`，确保滑动未生效与真实到底不会被混淆；若可稳定识别滚动条，应优先以滚动条到底作为结束证据。
- 分别验证列表中有重复礼装实例、存在新礼装但目录缺模板、以及模板分数刚好位于 0.88 附近的场景，确认输出中的唯一种类数、未匹配格数和告警含义不会混淆。
