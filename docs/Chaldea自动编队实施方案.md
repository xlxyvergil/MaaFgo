# Chaldea 自动编队实施方案

## 1. 目标与边界

新增“自动编队”能力：独立的“Chaldea 自动编队”任务仍可从 FGO 的**编队界面**
启动；同时把相同能力接入全部使用“原生自动战斗”的战斗模块。战斗模块先导航到
助战界面并完成助战选择，到达编队界面后按开关决定是否读取 Chaldea 导入的
`BattleShareData`，把游戏内六个编队槽位调整为攻略所需布局；成功复核后再进入战斗。

本功能负责从者、助战位置、本地从者的概念礼装与数据指定的御主礼装；不负责
从者等级、技能等级、御主礼装等级或助战人物/助战礼装的选择。

因此玩家应在运行前将不希望选中的同名低等级从者移出从者列表（例如放入保管室）。
自动编队按从者身份和头像定位，无法在多个同名从者之间按等级或技能等级择优。
在从者列表查找时，同屏存在多个高匹配的同名从者候选（含不同灵基），连续两帧确认
后停止选择，输出
`servant_duplicate_candidates`、从者名称/ID及前两名分数，明确要求玩家自行整理，
仅保留需要使用的一名后重试；不再滑动到查找上限并误报“未找到”。该保护仅针对
当前可见的多个高分候选，不能保证发现其他屏幕上的重复从者。

编辑页还是队伍确认页。正常返回编辑页时继续原流程；若返回带“配置变更”的确认页，

已确认的规则：

1. 每个槽位仅在“从者/助战类型正确”且“位置正确”时才算匹配。
2. 先处理已在队伍内、但位置错误的从者，以及已选助战的位置；完成重排后，
   再替换人物不匹配的本地从者。
3. 助战必须校验人物身份。Chaldea 显式提供 `SUPPORT` 时，当前助战的 `svtId`
   必须与其一致；身份无法识别或不一致时，在任何编队操作前停止。
4. 新增“是否用助战代替编队数据”选项，默认“否”以保持旧行为。选“是”且
   Chaldea 未显式提供助战时，当前助战可替代编队数据中一个同 `svtId` 的
   `LOCAL` 从者；找不到同 ID 目标、当前没有助战或身份无法识别时停止。
5. 选“否”且 Chaldea 未指定助战时，仍先把当前助战移至 Chaldea 未使用的
   `EMPTY` 槽位；若没有空位则失败退出。助战只移动已有成员，不负责从助战
   列表重新选择。
6. Chaldea 找不到从者头像资源时，必须安全失败，不能用低分图片匹配或名称
   猜测替代。

已提供的界面约定：

- 六个从者槽位 ROI：`[41,160,187,276]`、`[241,160,187,276]`、
  `[440,160,187,276]`、`[654,160,187,276]`、`[854,160,187,276]`、
  `[1055,160,188,276]`；
- 点击 `battle/配置变更.png` 命中的位置进入编辑状态；
- 以 `battle/助战标记.png` 判断助战；
- 交换方式：长按源槽的从者，拖动到目标槽中心；
- 全部完成后点击 `battle/编队决定.png`。

礼装规则：

1. 任务提供“自动编成礼装”总开关（默认开启）。关闭时，从者阶段完全复核后
   直接点击 `编队决定`，不会加载礼装数据库、匹配礼装图片或进入礼装选择界面。
2. 开启时，从者阶段完全复核后，才逐槽处理本地从者的礼装；六槽从者均不变后
   再点击 `编队决定`。
3. Chaldea 优先读取 `equip1.id`、`equip1.limitBreak`，兼容旧字段 `ceId`、
   `ceLimitBreak`。助战礼装不能替换，只记录跳过。
4. `EquipFaces/team` 用于在编队卡片中核对礼装，`EquipFaces/list` 用于仓库
   列表中定位；文件均按 `f_{equipId}0.png` 命名。
5. `agent/custom/equip_list.json` 由 `equip_list.csv` 的“非高价值礼装=0”生成。
   不在该表或缺少任一图片资源的礼装直接跳过并写日志。
6. 选择礼装时先重置筛选、按星级筛选，再按 CSV 的 `入手分类(日文)` 选择对应
   的礼装标签；映射后的标签与 `EquipFaces/礼装类别筛选项/*.png` 文件名一致。
   友情点召唤礼装在游戏筛选器中归入“通常”。目标为满破时，继续在筛选面板中
   上滑寻找并点击 `EquipFaces/满破判断.png`，否则不选择该条件。仓库定位每次仅
   滑动约一排卡片，最多 30 次；从者定位的滑动策略不受影响。
7. 若满破筛选后仓库没有目标礼装，可由任务选项选择“跳过”或“改查非满破版本”；
   两次都找不到时安全返回编队页并写日志，不会停在列表界面。
8. Chaldea 槽位包含 `grandSvt: true` 时，该冠位从者或冠位助战只按 `svtId` 和槽位
   匹配，`equip1`、`equip2`、`equip3` 均不进入目标礼装检查、替换或卸下流程；即使
   分享数据声明了礼装也默认视为满足。助战替代把本地目标转换为 `SUPPORT` 时，若实际
   助战是冠位助战，也按同一规则跳过礼装。
9. 普通礼装入口点击槽位后，不再只等待礼装仓库：轮询“礼装选择页已到达”和
   `battle/冠位助战礼装编辑弹窗.png` 两个互斥结果。命中选择页时继续原流程；命中冠位
   弹窗时通过一次 ESC/Android Back 关闭，将该槽标记为冠位并视为礼装已满足。
10. 第 9 条是界面兜底，不依赖 Chaldea 的 `grandSvt` 是否准确；因此实际为冠位的本地
    从者即使源数据未标记，也不会误入普通礼装仓库或导致礼装编成失败。

## 2. Chaldea 数据到六槽位的映射

Chaldea 的 `team` 字段提供两个固定长度为 3 的数组：

| 游戏槽位（1-based） | Chaldea 字段 | 数组下标 | 内部下标 |
| --- | --- | --- | --- |
| 1–3，前排 | `team.onFieldSvts` | 0–2 | 0–2 |
| 4–6，候补 | `team.backupSvts` | 0–2 | 3–5 |

每项取 `svtId` 作为本地从者身份；前排的 `supportType` 为 `friend`、`fixed`
或 `npc` 时，该项是攻略要求的助战槽。`null` 表示攻略未指定该槽的从者。

自动编队应先将导入数据转换成如下内部规格，后续界面逻辑只消费这份规格：

```text
expected[0..5] = {
  kind: LOCAL | SUPPORT | EMPTY,
  svt_id: int | null,       # LOCAL 与 SUPPORT 均使用
  equip_id: int | null,     # 仅 LOCAL 的本地礼装
  equip_limit_break: bool,
  grand_svt: bool,           # Chaldea 标记的冠位从者/助战
  source_position: 0..5
}
```

其中：

- `LOCAL`：`supportType` 不是 `friend/fixed/npc`，必须按 `svtId` 匹配；
- `SUPPORT`：槽位必须含有助战标记，且人物 `svtId` 必须一致；
- `EMPTY`：不校验该槽最终内容；可容纳当前已选助战。
- `grand_svt=true`：该槽仍按 `kind` 和 `svt_id` 编排从者，但所有礼装字段均忽略。

构建原始规格后，再根据选项处理未显式带助战的数据：

- “是否用助战代替编队数据=否”：规格不变，当前助战稍后移至 `EMPTY`；
- “是否用助战代替编队数据=是”：先识别当前唯一助战身份，在原始规格中寻找
  同 `svtId` 的 `LOCAL`。优先选择助战当前所在且 ID 相同的目标槽，否则选择
  第一个同 ID 槽位，并把该目标的 `kind` 转为 `SUPPORT`；原槽位、礼装字段和
  `svt_id` 均保留，后续重排会将助战移至此处；替代后的助战礼装无条件忽略，
  不要求额外判断它是否真为冠位从者；
- Chaldea 已显式包含 `SUPPORT` 时不做替代转换，选项只影响“不带助战格式”。

这与现有转换器的 0–5 顺序一致，见
[`agent/chaldea/bbc_formatter.py`](../agent/chaldea/bbc_formatter.py)。

## 3. 运行时识别模型

进入编队页后，从一张截图建立 `current[0..5]`：

```text
current[i] = {
  kind: LOCAL | SUPPORT | EMPTY | UNKNOWN,
  svt_id: int | null,
  confidence: float
}
```

### 3.1 从者识别

- 使用 `assets/resource/base/image/NarrowFigures/` 中的立绘；命名与
  `servant_face` 一致，按 `f_*.png` 枚举同一 `svtId` 的全部可用形态和灵基
  阶段。
- 识别只在该槽位的 ROI 中进行，取高于阈值的最佳模板；记录匹配分数、文件名
  与坐标，便于排查误判。
- `NarrowFigures` 缺少目标图片时，可选择性尝试 `servant_face` 的同名资源作
  兼容回退；两者皆缺则产生 `resource_missing(svtId, slot)` 并停止。
- `UNKNOWN` 绝不参与重排或替换决策。出现低置信度/无法识别时停止，避免误操作。

### 3.2 助战和空槽识别

- 助战先由 `battle/助战标记.png` 在各槽位 ROI 中判断类型，再用目标从者的
  `NarrowFigures`/`servant_face` 模板识别人物 `svtId`。只允许高于从者阈值
  的最佳命中；不能仅凭助战标记推断人物正确。
- 空槽同样必须有专用模板或可靠的视觉判定。
- 识别优先级为：空槽 → 助战标记并识别其人物 → 本地从者头像；这样助战不会
  被误当作本地从者，同时保留身份供前置校验。

### 3.3 槽位匹配定义

| 目标 `expected[i]` | 当前 `current[i]` | 是否匹配 |
| --- | --- | --- |
| `LOCAL(id)` | `LOCAL(id)` | 是 |
| `SUPPORT(id)` | `SUPPORT(id)` | 是 |
| `EMPTY` | 任意 | 是，不参与最终校验 |
| 其他任意组合 | 任意 | 否 |

## 4. 状态机与操作顺序

### 阶段 A：前置校验

1. 下载/解码 Chaldea 分享链接，构建 `expected`；若没有有效的 `team` 或六槽
   数据类型异常，失败退出。
2. 确认当前画面为编队界面；不从主界面或战斗页擅自导航。
3. 识别全部六槽，并在任何点击前校验当前唯一助战身份。显式助战目标要求 ID
   一致；替代模式要求当前助战 ID 存在于某个 `LOCAL` 目标；任何身份未知、
   ID 不一致、缺资源或助战数量异常都停止。
4. 替代模式校验通过后，将对应目标从 `LOCAL(id)` 转为 `SUPPORT(id)`；关闭
   替代且数据无助战时保持原规格，稍后把助战移至 `EMPTY`。
5. 输出初始布局，例如 `当前=[LOCAL(100100), SUPPORT(4000100), ...]` 与目标布局，
   便于用户核对。
6. 若目标本地从者至少一半不在当前队伍，先尝试通过“编队编辑 → 编队解散 → 二次确认”
   清空后重建。冠位从者所在队伍不支持解散：点击“编队解散”后 5 秒内未出现二次确认，
   且已确认仍处于编队编辑页时，将本次清空记为 `skipped`，刷新当前六槽后继续阶段 B/C
   的增量换位和替换。Grand Duel 的 `LIMITED` 编队若连“编队编辑”入口都不响应，
   但仍稳定停留在编队确认页，也将清空记为 `skipped`，随后改点“配置变更”进入逐槽
   编辑。只有编辑页和确认页都无法确认时才按清空失败终止。清空链各节点
   使用空 `on_error` 阻断全局恢复链，返回后必须复核实际页面，不能只依据子任务的
   `succeeded` 状态判断清空成功。

### 阶段 B：优先重排已有成员

本阶段不打开从者选择页，只交换当前队伍中已有的卡位。

1. 固定所有已匹配槽位。
2. 在剩余槽位建立“当前项目 → 目标项目”的多重集合匹配：本地从者以 `svtId`
   为键，助战以唯一的 `SUPPORT` 标记为键，空位以 `EMPTY` 为键。
3. 对能够让目标槽直接匹配的项目执行交换；环状错位（如 `A,B,C → B,C,A`）
   按实际 UI 支持的交换原语逐步消解，并在每次交换后重新截图验证。
4. 重复从者只按数量配对，不依赖“第几个相同从者”的虚假身份；任意一个相同
   `svtId` 到达目标槽即可。
5. 每次操作只允许影响指定的两个槽位；如果复核发现其他槽改变，立刻停止。

助战属于阶段 B 的普通可移动项目：例如最终目标要求 `SUPPORT(4000100)` 在槽 2、
当前同 ID 助战在槽 1，则长按槽 1 并拖至槽 2 中心。若关闭替代且 Chaldea 未
指定助战，则先将其移至任一 `EMPTY` 目标槽，再开始本地从者替换；若 Chaldea
没有空位则安全失败。

### 阶段 C：替换本地从者

阶段 B 后，只有 `expected[i] == LOCAL(id)` 且当前不是该 `LOCAL(id)` 的槽位
进入替换队列。每个槽位独立完成以下流程：

1. 点击该编队槽，进入从者选择界面；以页面标记确认进入成功。
2. 根据 `servant_list.json` 中对应 `svtId` 的星级/职阶进行筛选；筛选前重置旧
   条件，筛选后确认列表已刷新。
3. 枚举目标从者在 `servant_face` 中的全部可用头像。仓库查找不得对整张截图做
   158×158 完整模板滑窗：列表卡片上的职阶、等级、锁定和 COST 会遮挡模板，页面标题
   也可能产生高分假命中。应复用羁绊补齐的卡位特征算法：先由黄色 `Servant` 条带
   推导当前完整卡片行，再在六列固定卡位内提取头像内部特征，与目标头像进行归一化
   比较；匹配分不低于 `0.88` 且与次优卡位保留至少 `0.12` 分差时才作为候选。
4. 候选必须在间隔截图中保持同一模板、同一卡位，才允许点击。未命中时每轮只下滑
   一次并等待列表稳定；下滑距离采用约 `342px`（原 `360px` 缩减 5%），为相邻页面
   留出重叠区域，避免目标长期停留在屏幕边缘的残缺行。
5. 点击候选头像后，必须确认已返回编队页且目标槽更新为该从者；否则不继续。
6. 重新识别六槽后处理下一项，防止界面排序或自动换位造成陈旧判断。

`SUPPORT` 与 `EMPTY` 均不进入本地从者替换队列。目标助战未出现时，按当前边界
报错；`EMPTY` 目标不执行清空操作。

### 阶段 D：概念礼装编队、最终复核与衔接战斗

从者位置完全匹配后，逐个 `LOCAL` 槽位检查 `EquipFaces/team` 中的目标礼装。
不匹配时点击该卡片下部的礼装区域进入礼装选择页，按星级及满破要求筛选，在
`EquipFaces/list` 中滚动匹配并选择；选择成功后必须返回编队页并复核。数据库
没有记录、缺资源、仓库无该礼装都不会中断从者成果，按规则记录跳过。

Chaldea 已标记为冠位的槽位和所有助战槽位在本阶段直接跳过。其余本地槽位点击礼装
区域后同时等待选择页标志与冠位礼装弹窗；若出现弹窗，则关闭弹窗、把该槽动态记为
冠位并视为目标礼装满足，不再进入仓库、筛选或执行返回编队后的普通礼装模板复核。

### 阶段 E：羁绊最大化中的冠位礼装

2026-10-17 补充国服弹窗模板：`cn/image/battle/冠位助战礼装编辑弹窗.png`。最终来源为用户更正的原生 1280×720 报错截图 `2026.10.17-17.14.54.578_羁绊补齐-取消变更确认 (1).png`，直接裁取 `[332,234,646,31]` 三栏中文标题，不缩放、不包含礼装卡面；此前误发的 2560×1440 截图不再用于正式模板。通过现有资源选择及 `_equip_entry_state` 离线验证，国服优先加载 cn 覆盖并判定 `grand`，匹配约 1.000，高于既有 0.80 阈值；日服继续加载 base 日文模板。旧日文模板在这张国服截图中仅 0.3472。本次未进行实机点击测试。

基础自动编队附带的羁绊补齐，以及独立“自动补齐从者礼装（按照羁绊最大化）”任务，
共用以下冠位处理规则：

1. 点击本地从者的礼装位后，若出现 `battle/冠位助战礼装编辑弹窗.png`，在弹窗 ROI
   `[267,218,776,171]` 内使用编队礼装模板识别目前携带的礼装，数量允许为 0～3 张；
   其中识别出的常驻羁绊礼装计入当前基线、去重约束和后续羁绊配置计划。
2. 冠位本地从者的预设礼装不可由普通礼装仓库流程修改；读取完成后通过一次 ESC/Back
   关闭弹窗，并将该从者礼装位锁定。即使开启“修改所有礼装”，也不卸下或重配这些礼装。
3. 冠位助战整槽忽略：不识别其弹窗礼装、不计入羁绊收益、不参与礼装去重，也不执行

## 5. 与现有代码的集成点

### 5.1 战斗模块的选项结构

所有复用 `battle_mode` 的日常战斗、通用活动、冠位戴冠战、直接战斗等任务，
在选择“原生自动战斗”后统一显示以下并列选项，顺序固定为：

```text
原生自动战斗
├─ 战斗次数
├─ 跳过剧情
├─ 是否使用 Chaldea 队伍
│  └─ 是
│     ├─ Chaldea 队伍导入
│     └─ 编队方式（默认：手动）
│        ├─ 手动
│        └─ 自动
│           ├─ 是否用助战代替编队数据
│           ├─ 自动编成礼装
│           │  └─ 是：满破礼装缺失时（默认：改查非满破版本）
│           └─ 自动补齐从者和羁绊礼装
│              └─ 自动记忆（默认：是）
└─ 助战方式
   ├─ 首个助战
   ├─ 自定义助战：显示既有助战筛选项
   └─ 使用 Chaldea 配置
```

- “跳过剧情”只控制剧情跳过节点，不再包含“助战方式”子选项；两者互为并列
  模块，切换剧情选项不得隐藏、重建或覆盖助战选项。
- “是否使用 Chaldea 队伍”默认“否”。选“否”时不显示导入和编队方式，
  并保持原有“选择助战后直接点击开始任务”的行为；选“是”时显示
  “Chaldea 队伍导入”和紧随其后的“编队方式”。
- “编队方式”默认“手动”。选“手动”时
  不显示助战替代、礼装和羁绊补齐等自动编队专属选项；选“自动”时才显示这些
  选项并执行完整自动编队。
- “自动编成礼装”关闭时不展示也不执行“满破礼装缺失时”；开启时默认改查非满破版本，
  仍可显式选择跳过该礼装。独立自动编队任务也采用相同层级和默认值。
- “自动记忆”仅在开启羁绊补齐后显示。完整优化成功后保存六槽签名；相同有效配置下
  阵容一致时跳过重复优化，但仍检查 Chaldea 未指定位置上的额外从者是否满羁绊。
- “助战方式”始终位于 Chaldea 模块之后并与其并列。新增“使用 Chaldea 配置”只影响
  助战列表选人，不隐式开启 Chaldea 队伍导入或自动编队；首个/自定义助战行为保持原样。
- “使用 Chaldea 配置”要求本次任务已开启“是否使用 Chaldea 队伍”，且已填写可读取的
  导入来源；否则在助战节点直接失败，不能退回首个助战或继续战斗。队伍六槽中必须恰有
  一个 `supportType=friend/fixed/npc` 的有效助战；无标记或多标记同样失败。
- 该方式复用现有助战筛选能力：按 `svtId` 选头像与职介，按数据中提供的 `lv`、
  `tdLv`、`skillLvs`、`appendLvs` 设定最低等级，按普通助战的 `equip1/ceId` 或
  冠位助战的 `equip1`、`equip2` 匹配礼装及各自的满破状态。缺少的可选数值不施加
  条件；数据明确指定礼装但名称或图像模板不可用时直接失败。冠位第三格 `equip3`
  暂无可按礼装 ID 识别的助战筛选能力，因此不声称已校验该格。
- 独立的“Chaldea 自动编队”任务保留原选项与入口，不套用战斗模块的总开关。
- 单次原生自动战斗入口没有“战斗次数”；其余层级和顺序与连续/通用战斗入口一致。

### 5.2 战斗流程接入

开启 Chaldea 队伍后的第一场战斗按“编队方式”分为两条流程：

```text
手动：章节/关卡导航 → 助战选择 → 编队页 → Chaldea 编队核对
      →（仅位置不一致时换位并保存）→ 点击开始任务 → 原生自动战斗
自动：章节/关卡导航 → 助战选择 → 编队页 → Chaldea 自动编队
      → 点击开始任务 → 原生自动战斗
```

连续出击第二场及以后若游戏从助战页直接进入战斗、没有出现编队页，则不会误触发
编队处理；是否执行由“编队开始按钮已出现”这一正向识别结果决定。

接入点采用独立的“编队处理调度”节点：基础行为直接进入原有“点击开始任务”节点，
“是否使用 Chaldea 队伍=是”只负责展示导入项和“编队方式”，由“编队方式=手动”
将调度节点指向 `执行手动编队检查`，由“编队方式=自动”指向 `执行自动编队`；两条
分支完成后都回到原有点击节点。该选项不覆盖 `进本流程.next`，因此不会和
“首个助战/自定义助战”对同一字段产生覆盖顺序依赖；任一编队处理失败时 Action 直接失败，
不得继续点击开始任务或进入战斗。

`执行手动编队检查` 必须显式配置空 `on_error`。否则项目默认的 `Global_Null`
错误恢复链会在 Action 失败后继续执行，并可能把最终任务状态改写为成功；空错误分支
确保身份不匹配时保持失败状态并立即停止。

手动编队核对遵循以下边界：

- 只核对从者身份和位置，不选人、不清空编队、不编成礼装，也不执行羁绊补齐。
- 先以多次稳定识别结果确认 Chaldea 指定的全部本地从者（含重复数量）都在当前
  六槽；缺少目标从者时立即失败，日志同时输出当前和目标六槽，不得为了凑齐身份进入
  仓库选人。Chaldea 未指定的槽位不要求为空，其中已有的其他本地从者继续保留。
- Chaldea 明确包含助战时，当前助战从者身份也必须匹配；数据不包含助战时，沿用既有
  规则把已选助战视为额外成员，只允许其占用 Chaldea 未使用的空位，不启用“助战替代”。
- 只有“Chaldea 目标身份齐全、但位置不同”时才进入配置变更，复用自动编队的拖动换位和
  多次复核逻辑；位置全部匹配时不打开编辑页，直接继续。
- 完成换位后必须再次稳定核对全部目标槽位并点击“编队决定”保存；复核失败则停止任务。

### 5.3 兼容性边界

- Chaldea 下载和解码复用 `agent/chaldea/chaldea_client.py` 的
  `fetch_share_data`，而非再次实现链接/短 ID/压缩数据解析。
- `agent/chaldea/bbc_formatter.py` 已有 `onFieldSvts + backupSvts` 的顺序转换，
  自动编队应抽取/复用相同的队伍规格构造逻辑，避免两个入口的槽位解释漂移。
- 原生自动战斗当前通过 `Chaldea导入手动输入` 输入框把
  `chaldea_import_source` 注入 `auto_battle`。新增自动编队节点应在
  “执行原生自动战斗”之前使用同一参数，并将已解码的队伍规格传给后续步骤，
  避免重复下载。
- 从者选择和多形态图片定位参考
  `agent/custom/servant_up_action.py`；建议抽取共享的图片枚举/匹配工具，避免
  复制两份逻辑和阈值。
- 编队界面已有 `battle/配置变更.png`、`battle/编队决定.png` 和
  `battle/助战标记.png`；脚本使用新的独立 Action，点击与筛选交给新的专用
  pipeline，不修改原生自动战斗 Action。
- `原生自动战斗跳过剧情` 的 pipeline override 仅保留跳过节点的启停；
  `原生自动战斗助战方式` 继续只选择助战路径；Chaldea 总开关除控制选项展示外，
  还向 Chaldea 助战节点传入显式启用标记，以拒绝“未开启导入但选了 Chaldea 助战”的组合；
  “编队方式”的手动/自动分支各自控制编队处理调度和结束出口。各选项写入不同节点，
  防止 option 顺序影响原功能。

## 6. 错误处理与日志

以下情况必须终止，且不得继续原生战斗：

| 错误码 | 条件 |
| --- | --- |
| `invalid_chaldea_team` | 导入数据缺少/损坏 `team` 或槽位结构异常 |
| `not_on_formation_page` | 启动时不在编队界面 |
| `resource_missing` | 目标本地从者或必须校验的助战没有 NarrowFigures 与回退头像资源 |
| `slot_unknown` | 任一槽位无法可靠识别 |
| `support_missing` | 目标要求助战但当前没有可移动的助战 |
| `support_count_invalid` | 当前助战数量与可处理范围不符 |
| `support_identity_unknown` | 当前助战头像无法识别为目标集合中的任何从者 |
| `support_identity_mismatch` | 显式助战 ID 不一致，或替代模式中没有同 ID 本地目标 |
| `manual_formation_servant_mismatch` | 手动编队中缺少 Chaldea 指定的目标从者 |
| `manual_formation_reorder_failed` | 手动编队仅需换位，但换位后稳定复核仍不通过 |
| `swap_verify_failed` | 交换后复核失败或影响了非目标槽 |
| `servant_not_found` | 筛选/滚动达到上限仍未找到目标从者 |
| `equip_replace_verify_failed` | 已选择礼装但返回编队页后模板复核不通过 |
| `final_formation_mismatch` | 最终六槽复核不通过 |

日志至少记录：Chaldea 目标六槽、初始/每次操作后的六槽、操作类型和涉及槽位、
头像模板最高分、资源缺失文件名、最终复核结果。

## 9. 御主礼装（2026-10-31）

`agent/custom/mystic_code.py` 读取 `team.mysticCode.mysticCodeId`，兼容顶层
`mysticCode.id`；缺失、空值与 ID 0 不产生匹配要求，仅记录等级也不检查。
自动编队在从者和概念礼装保存后检查/更换御主礼装，成功后才发布最终编队；
手动编队在换位或保存之前只读检查，不匹配输出用户提示并失败停止。
该要求独立于概念礼装的 `auto_equip` 开关。

`御主礼装.json` 保存打开、页面检测、横向拖动与返回动作，公共入口通过
`next` 执行识别，避免 `Context.run_task()` 入口跳过识别。底部列表实测为循环
列表，无固定起点；从当前页开始向左查找，最多10页，相邻页面保留重叠。
识别连续两帧稳定才点击，选择后复核中上部图标，返回后再复核编队左下角。
两个动作后的复核最多8轮，允许资源加载期间先收到旧缓存帧；阈值均为0.90。
未持有、资源缺失、识别失败均原地停止，提示不触发返回或通用恢复。
