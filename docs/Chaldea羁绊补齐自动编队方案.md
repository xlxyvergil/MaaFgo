# Chaldea 羁绊补齐自动编队方案

## 1. 目标、边界与结论

在现有「Chaldea 自动编队」成功完成后，提供一个可选的第二阶段：在**不替换
Chaldea 已指定从者、助战或礼装**的前提下，使用剩余的本地从者位和未占用的礼装
位，并按用户选项决定是否优化 Chaldea 未指定位置上已有的从者或礼装，尽量提高五名
本地从者的单次羁绊点总和。

羁绊业务逻辑仍全部位于独立的 Custom Action 中，不向
[`agent/custom/formation_action.py`](../agent/custom/formation_action.py) 插入规划、
库存或羁绊计算代码。实机测试发现确认页的「开始任务」与编辑页的「编队决定」会被同一
模板高分命中，因此原 Action 只增加一个页面定界修正：检测到确认页专有的
`battle/配置变更.png` 时，必须先进入配置变更，不能把该页当作编辑页点击。
原 Action 仍会自行点击一次「编队决定」，因此新 Action 的运行方式是：

```text
现有 Chaldea 自动编队成功并确认
  -> 新 Action 重新进入“配置变更”页
  -> 按选项读取个人从者库/礼装库，校验失败则对应类别回退实时扫描
  -> 识别 COST、可补空槽、现有羁绊礼装
  -> 规划并补齐从者/礼装
  -> COST 与羁绊复核
  -> 再次点击“编队决定”
```

页面定界属于两阶段之间的集成保护，不改变第一阶段的编队业务，也不把羁绊功能耦合进
原脚本。人数不足弹窗只允许在真正点击「编队决定」后轮询并使用通用 `决定.png` 确认；
若仍处于确认页则绝不能先点击「开始任务」。

这是一种两阶段提交：即使新功能在 OCR、资源或仓库查找阶段失败，第一阶段已完成
的 Chaldea 队伍不会被回退或被旧脚本改写；新 Action 只会在安全条件满足时继续。

范围：

- 仅处理六槽中的本地从者；助战不选择、不替换、不编辑其礼装，且完全不进入
  羁绊计算范围。助战携带的礼装效果也不作为本地从者的收益来源。
- Chaldea `team` 中未指定本地从者的位置若为 `SELECT`，始终可以补齐；若残留旧从者，
  则由“自动修改其他位置从者”决定替换或锁定。锁定对象必须先识别并参与后续评分。
- Chaldea 已显式配置 `equip1/ceId` 的本地槽位永远受保护，即使礼装自动编队开关
  已关闭也不允许本功能覆盖该槽位。
- Chaldea 未指定礼装但当前已有礼装的位置，由“自动修改其他位置礼装”决定先卸下重算
  或保持固定；真正的空礼装位仍可用于补齐。
- 仅使用本地数据中有实际羁绊公式、且列表与编队模板均齐全的礼装。
- 不使用 `event_id` 条件的活动限定羁绊效果；它们已归档，但默认不作为常驻收益。

## 2. 新选项

在 `Chaldea 自动编队` 任务新增一个总开关和六个仅在开启时显示的子选项：

| 选项 | 类型 | 默认值 | 作用 |
| --- | --- | --- | --- |
| `自动补齐从者和羁绊礼装` | 是/否 | 否 | 否时新 Action 直接成功返回，不产生点击。 |
| `补齐从者优先X星` | 0–5 星 | 5 星 | 每次补人先尝试该星级；若无可选项，再按 5→0 星、跳过已尝试星级的顺序回退。 |
| `羁绊基础值` | 正整数输入 | 1200 | 用于比较固定值与百分比羁绊礼装；作为 `bond_base` 传给新 Action。 |
| `使用本地从者库` | 是/否 | 否 | 读取 `config/Inventory/player_servants.json`，在已知持有集合内规划，只定位最终目标，不再先完整扫描各星级。 |
| `使用本地礼装库` | 是/否 | 否 | 读取 `config/Inventory/player_equips.json`，只在已知持有集合内规划，跳过不点击的库存预检，直接定位最终礼装。 |
| `自动修改其他位置从者` | 是/否 | 是 | Chaldea 未指定位置残留旧从者时，是则允许替换；否则锁定原从者并以其特性继续计算。真正的 `SELECT` 空位不受此项影响。 |
| `自动修改其他位置礼装` | 是/否 | 是 | Chaldea 未指定礼装的位置已有礼装时，是则在首次规划前卸下并重新优化；否则锁定原礼装。真正的空礼装位不受此项影响。 |

例如优先 3 星时，尝试顺序为 `3, 5, 4, 2, 1, 0`。星级是**候选优先级**，不是
无视 COST 的强制要求：每个候选仍必须通过预估 COST 和实际 OCR COST 校验。

开关应在原自动编队完成后才触发新节点；原「自动编成礼装」关闭时，原流程仍视为
礼装阶段完成，新功能照常运行，但会保护 Chaldea 分享数据中已声明的礼装槽位。
两个“自动修改其他位置”选项在读取 Chaldea 数据后、首次羁绊与 COST 规划前生效；默认
为“是”以保持原先允许优化未指定位置的行为。

两个“使用本地库”开关互相独立且默认均为“否”，以保持旧用户行为。选择“是”仅在
对应 JSON 通过结构和完整扫描校验后启用快速模式；文件不存在、JSON 损坏、版本/类别
不匹配或 `scan_complete != true` 时，只对该类别回退现有实时扫描，并用 Focus 日志明确
提示。库存发生召唤、出售或礼装满破变化后，用户应重新执行“构建个人从者礼装库”。

## 3. 需要的新文件与数据

实现时只新建以下文件，不在原自动编队 Python 文件中插入羁绊逻辑：

| 文件 | 职责 |
| --- | --- |
| `agent/custom/bond_completion_action.py` | 新 Custom Action，负责识别、规划、选择与复核。 |
| `agent/custom/bond_matcher.py` | 无 UI 依赖的纯函数：从者特性归一化、礼装目标匹配、羁绊评分、候选排序。 |
| `agent/custom/bond_completion_costs.json` | 由 Atlas 离线生成的 `servant_id/equip_id -> cost` 索引；运行时绝不联网。 |
| `tools/update_bond_completion_costs.py` | 增量更新上述 COST 索引的维护工具。 |
| `assets/resource/base/pipeline/羁绊补齐自动编队.json` | 新 Action 专用 pipeline：进入/退出选择页、筛选、复位顶部、单次下滑、等待、筛选确认与最终决定。 |
| 独立 option/task JSON | 新 Action 的入口、开关与 OCR 调试节点；不改变原 Action 的业务代码。 |

`羁绊补齐自动编队.json` 的节点可从现有 `自动编队.json` 的同类流程复制，但必须使用
独立的 `羁绊补齐-` 节点名。新 Action 不直接调用或覆盖既有 `自动编队-*` pipeline，
避免同时运行、覆盖动态筛选参数或以后调整原流程时产生隐式耦合。

现有数据的使用方式：

- `servant_list.json` 提供 `id`、职阶、星级、图片与 `bond` 特性；当前不含 COST，
  因而由 sidecar 索引补齐。
- `equip_list.json` 提供礼装 ID、星级、筛选分类及 `bond`。`bond.bonus_type !=
  "none"` 的常驻效果才进入候选；`atlas_effects` 仅用于审计和排除活动条件。
- `config/Inventory/player_servants.json` 与 `player_equips.json` 是可选的玩家持有集合。
  快速模式只信任其中的 ID；名称、星级、COST、特性和羁绊公式仍以工程目录数据为准，
  避免旧库存文件冻结业务数据。
- `FGO牵绊计算器（优化版）.html` 仅作为公式和目标匹配规则的参考来源；运行时不
  执行 HTML/JavaScript，也不从网页读取数据。

新 Action 直接读取现有编队礼装使用的 `EquipFaces/list` 与 `EquipFaces/team` 资源，
不复制图片文件。2026-09-05 的开发资源实测：59 张常驻羁绊候选中 16 张同时具备
list/team 模板，另外 43 张新增归档记录尚未落入这两个图片目录；运行时会逐项校验，
缺图对象明确记录 ID 并跳过，不会误点仓库首项。以后补入对应图片即可自动扩大候选池。

## 4. 状态与界面识别

### 4.0 本地库存文件契约

快速模式读取构建任务生成的 schema v1 文件。启用条件为：文件可读、顶层
`schema_version == 1`、`kind` 与类别一致、`scan_complete == true`、对象数组存在，且
每条候选至少有非空 ID。`count` 必须与去重后的 ID 数一致；不满足时整体拒绝该类别的
本地文件并回退实时扫描，不能部分读取损坏文档。

`catalog_complete=false` 不代表扫描失败：它表示工程目录中仍有缺少识图模板的对象。
此时允许使用已经可靠识别的 ID，但应提示“本地库可能漏掉缺模板对象”，最终最优性只
针对已知持有集合。`generated_at` 仅用于日志展示，不设置自动过期时间。

礼装文件的 `limit_break_known=false` 表示只知道玩家持有该种礼装，不能证明满破。
快速模式仍按现有满破筛选定位；若本地记录的礼装在当前筛选下找不到，则从本轮候选池
移除并联合重规划，不把相似礼装或非满破版本当成目标。

### 4.1 槽位与保护规则

复用既有六个从者槽 ROI 和礼装 ROI。新 Action 重新读取 Chaldea 分享数据，建立：

```text
protected_servant_slots = Chaldea 指定 LOCAL 或 SUPPORT 的槽位
protected_equip_slots   = Chaldea LOCAL 槽中 equip_id 非空的槽位
fillable_slots          = Chaldea EMPTY 且游戏识别为 SELECT 的非助战槽位
replaceable_slots       = Chaldea EMPTY、游戏存在 OTHER，且允许修改其他从者
locked_other_servants   = Chaldea EMPTY、游戏存在 OTHER，且禁止修改其他从者
fillable_equip_slots    = 本功能新填从者的空礼装位
                         + 非 protected_equip_slots 的现有本地从者空礼装位
                         （助战槽永远不在此集合中）
modifiable_equip_slots  = Chaldea 未指定礼装、当前已有礼装，且允许修改其他礼装
locked_other_equips     = Chaldea 未指定礼装、当前已有礼装，且禁止修改其他礼装
```

真正的 `SELECT` 空位还必须满足“当前全队本地从者少于 5”；替换 `OTHER` 不增加人数，
不受该数量限制。残留 `OTHER` 无论是否允许替换，都要先用全量编队头像模板确认 ID、
特性和 COST：禁止修改时固定参与优化，允许修改时作为被替换对象参与净收益和 COST
计算。无法唯一识别时安全中止，不能忽略该成员后继续声称最大化。

允许修改其他礼装时，首次评分先记录原队伍基线，再卸下所有 Chaldea 未指定且已占用的
本地礼装；每次卸下后重新读取 UI COST，释放的槽位和 COST 才进入从者/礼装规划。禁止
修改时，这些礼装固定参与评分；无法识别为常驻羁绊礼装的对象作为零羁绊效果的占用位
保留，并在最终用原始槽位截图复核没有变化。

空礼装位采用灰度离散度与饱和像素比例联合判断。真机实测空槽会因卡框和背景渐变达到
`sat_ratio=0.270`，因此饱和比例上限取 `0.30`，同时仍要求灰度标准差不超过 `35`；
不能只放宽单一颜色条件。即使前置分类异常，“卸下”及其确认识别也各自限定 6 秒，
不得让不存在的按钮造成无界等待。

### 4.2 COST OCR

每次计划前、每次选从者后、每次选礼装后，以及最终提交前，从截图的基准 ROI
`[915, 671, 154, 43]`（按屏幕比例缩放）运行 Maa `JOCR`。识别文本必须匹配：

```text
^\s*([0-9,]+)\s*/\s*([0-9,]+)\s*$
```

解析为 `used_cost / max_cost`。OCR 为空、格式不合法、`used > max` 或连续两次结果
不一致时，停止后续新增操作并保留当前编队；不得用估算值继续点击。

候选的 Atlas COST 只用于点击前的保守判断：

```text
used_cost + servant_cost + 已预留的礼装_cost <= max_cost
used_cost - 被替换从者_cost + 新从者_cost + 已预留的礼装_cost <= max_cost
used_cost + equip_cost <= max_cost
```

实际 UI COST 是唯一提交依据。COST 不足时按所处阶段恢复：

- 补从者阶段：跳过当前候选，在已扫描的拥有列表中换 COST 更低的从者；当前星级没有
  可放入对象时，继续按既定星级顺序扫描更低 COST 的其他星级，直到找到可用者或所有
  候选都放不下。
- 补礼装阶段：先放弃当前礼装并尝试收益次优且 COST 更低的礼装；仍超限时，只卸下本
  Action 新增的礼装，按“边际羁绊收益最低”顺序回退，直到 OCR 确认不超限。Chaldea
  指定礼装永远不卸下；运行前其他位置的已有礼装只会在对应选项为“是”时，于首次规划
  前统一卸下。

### 4.3 可用性与图片

从者或礼装只有在以下条件同时成立时才可被选择：

1. 数据库含 ID、星级、特性/公式和 COST；
2. 对应的列表图片模板存在；
3. 当前筛选后的仓库列表实际匹配到模板；
4. 点击后返回编队页，且截图复核成功。

找不到即标记为本轮 `unavailable`，后续规划不再重复尝试。礼装需同时有 list/team
模板；从者需有列表模板，选后在编队槽的模板复核也必须通过。

### 4.4 从者库存扫描

未启用或无法启用本地从者库时，从者的“拥有与否”不能由工程数据库推断，必须从游戏
仓库确认。每个星级采用两次查找：

1. 进入从者选择页后，运行专用 pipeline 复位列表顶部、重置筛选并仅选择当前星级。
2. Python 从初始稳定截图及之后每次稳定截图中，对**该星级优先级列表的全部候选从者**
   做模板匹配，收集全部命中的 `servant_id`；此阶段绝不点击从者卡。
3. 每轮截图扫描完，运行 pipeline 的“单次下滑 + 等待稳定”节点，再继续匹配；最多
   下滑 15 次。可额外以滚动条到底模板提前结束，但“15 次”是稳定的安全上限。
4. 扫描完整个当前星级后，才用已发现的全部拥有从者进行羁绊/COST 计算，选出唯一的
   最终目标。
5. 再运行“复位顶部” pipeline，以最终目标的模板执行第二次定位、下滑和选择；成功
   返回编队页后，必须做头像与 COST 复核。

若当前星级扫描结果为空，则先运行复位顶部 pipeline，再切换到下一个星级重新扫描。
若扫描到了从者但当前最优对象不满足 COST，则在已拥有集合内依次尝试更低 COST 对象；
当前星级全部放不下时继续下一星级。所有星级都无可放入对象才结束补人阶段。

启用本地从者库时，用文件中的 ID 预先建立各星级持有集合，直接执行第 4、5 步：先在
内存中算出最终目标，再回到列表顶部定位该目标。不会执行“先滑到底收集全部拥有从者”
的第一遍扫描。若记录中的目标在当前仓库找不到，目标定位过程中已经对同星级全部候选
做横向识别，因此复用这次顶部到末屏的稳定命中结果，一次性刷新该星级持有集合、批量
排除未出现 ID 并重新规划；不能对每个过期候选各自重复滑动 15 次。刷新后的最终目标再
回顶部定位，后续槽位复用刷新结果。所有点击仍需编队头像和 UI COST 复核。

### 4.5 礼装库存预检与可用性状态

礼装数据库和图片只能证明对象可被识别，不能证明玩家实际拥有。每轮 Action 为候选礼装
维护五种状态：

```text
UNKNOWN      尚未检查本轮库存
AVAILABLE    已完整定位并确认存在
UNAVAILABLE  正确筛选并完整扫描后确认不存在
FIXED        初始已装备且不允许修改
USED         本轮已经装备
```

临时方案依赖 `UNKNOWN` 礼装时，先借用任一本地从者的礼装位进入仓库，执行与正式查找
相同的“筛选 → 回顶部 → 首屏识别 → 有上限逐屏下滑”，但命中后不点击礼装，直接返回
编队页并缓存为 `AVAILABLE`。完整扫描仍未命中才记为 `UNAVAILABLE`；筛选、回顶、下滑、
页面状态或识别流程异常均记为失败，不能冒充“玩家没有”。

发现 `UNAVAILABLE` 后，将该 ID 加入本轮黑名单并立即重新规划。状态缓存在本次 Action
内，同一礼装不重复预检；已固定或已使用的同 ID 不能再作为另一张礼装使用。

启用本地礼装库时，文件 ID 是本轮礼装候选白名单：规划器不会考虑文件外的礼装，文件
内且满足工程数据/模板条件的对象初始即视为“已知持有”，从而跳过上述不点击预检并直接
进入正式定位。若正式定位未找到，可能是库存已变化或文件无法证明满破；此时把该 ID
降为 `UNAVAILABLE` 并重新规划，而不是把它当成不可恢复的识图异常。筛选、回顶、下滑
或页面状态本身失败时仍按异常中止，不能伪装成库存过期。

## 5. 羁绊计算模型

### 5.1 与参考计算器一致的常驻公式

对每名本地从者，按参考 HTML 的顺序计算：

```text
step1 = 前排 ? 20% : 0%
intermediate = floor(bond_base * (1 + step1))

step2 = 所有已装备常驻百分比羁绊礼装中、对该从者匹配的百分比之和
result = floor(intermediate * (1 + step2)) + 所有 flat_per_servant 固定值
team_score = 五名本地从者 result 的总和
```

`bond_base` 影响“+50 固定值”与百分比礼装之间的优先级。任务提供“羁绊基础值”输入，
默认 1200；用户可按具体副本修改。脚本必须在日志中写出最终采用值，输入不是正整数时
明确报错，不得静默猜测。

`team_score`、`step1` 与 `step2` 均只使用五名本地从者和本地礼装。助战的从者特性、
所在前/后排、礼装和礼装效果全部排除；因此不会触碰助战礼装 ROI，也不特别处理助战
午茶时光等效果。

### 5.2 特性匹配

`bond_matcher.py` 复刻参考工具的纯数据规则：

- `all` 匹配每名本地从者；
- 普通目标与从者的基础特性、阵营、性别、职阶、灵基和灵衣特性匹配；
- 组合目标单独判断：`lawful_good`、`lawful_female`、`chaotic_seven`、
  `star_or_evil`、`beast`；
- `flat_per_servant` 不以从者特性筛除，按每位本地从者累计；
- 带 `event_id` 的 Atlas 条件默认排除，直到将来显式增加活动选择器。

对于新增从者，点击的图片模板会记录灵基/灵衣变体；评分取实际将被选中的变体，
而不是臆测最高特性。Chaldea 已指定从者的特性直接按其已知 ID 和当前可识别的变体
计算。Chaldea 未指定位置的残留从者必须通过全量模板唯一识别：最高分不低于编队复核
阈值，且相对第二候选保持安全分差；识别失败时中止，不能把它排除在比较之外。

## 6. 规划与执行算法

### 阶段 A：建立固定状态

1. 读取 Chaldea 队伍及全部任务选项；总开关关闭则立即成功返回。两个“使用本地库”
   选项先分别加载并校验库存文件，两个“自动修改其他位置”选项也在任何规划和编辑发生
   前确定。
2. 重新进入配置页，确认六槽、助战位置、真实空位、残留 `OTHER` 和保护礼装位。
3. 唯一识别残留从者并加入当前队伍模型；根据从者选项把它标记为可替换或锁定。
4. OCR 初始 COST；识别本地从者已装的候选羁绊礼装并计算修改前基线。
5. 根据礼装选项锁定其他位置已有礼装，或在规划前卸下它们并逐次复核 UI COST。
6. 载入满足数据和模板条件的常驻羁绊礼装候选；固定礼装不重复选取。

### 阶段 B：先规划礼装，再选择从者

为避免“先塞高 COST 从者，导致最优礼装装不下”，先按当前固定从者计算每张礼装的
边际团队收益；对最多可用的空礼装位进行有 COST 约束的束搜索（beam search）。
评分同时估计剩余空位可加入的从者对每张礼装目标的覆盖数。

在得到礼装组合后，按星级顺序为每个从者空位生成候选：

1. 先尝试用户优先星级；若该星级在完整扫描中没有任何匹配对象，才按 5→0 星回退。
2. 实时模式按第 4.4 节完整扫描当前星级；本地库模式直接使用对应星级的已知持有 ID。
   两种模式都必须先形成完整候选集合，不能点击“看起来最优”的第一名。
3. 同星级的实际拥有候选按“加入后 `team_score` 的增量、匹配礼装数、剩余 COST、ID”
   降序稳定排序，计算出唯一最终目标。
4. 最终目标依赖的礼装若尚未确认库存，先退出从者列表并按第 4.5 节预检；任一礼装
   不存在时，从礼装候选池排除该 ID，并重新计算当前槽位的从者与礼装联合排序。
5. 依赖礼装全部确认为 `AVAILABLE` 后，重新进入同星级从者列表，复位列表后只查找并
   选择最终目标；选择成功且 OCR COST 符合计划才入队。
6. 每成功选择一人就重新计算礼装组合和下一空位的星级扫描/排序。

替换其他位置从者时，排序前先从计算队伍中移除旧从者，候选预算使用
`剩余 COST + 旧从者 COST`，日志与复核使用 `新从者 COST - 旧从者 COST` 的实际净变化。
若允许替换但最终没有可用候选，旧从者仍保留并继续参加最终评分。

候选从者的尝试顺序严格服从用户指定星级；束搜索只决定同一优先层内、并且已经通过
完整仓库扫描确认拥有的从者之间的“羁绊最大化”排序，不能跳过优先星级直接选择更高
收益的其他星级。

### 阶段 C：补齐礼装

从者阶段结束后再次 OCR COST，并基于实际已选从者重新求解礼装组合：

1. 所有 Chaldea 指定礼装位绝对固定；其他位置已有礼装仅在选项为“否”时固定。
2. 仅将新选从者的礼装位和确认为空、非保护的本地礼装位加入可填集合。
3. 以 `team_score` 边际增量/COST 为主排序；每种本地礼装最多使用一张，不识别或利用
   同名礼装的多副本。
4. 实时模式对最终方案中的未知礼装先执行不点击的库存预检；本地库模式的候选已经由
   持有 ID 白名单限定，直接执行“筛选 → 模板查找 → 选择 → 编队图复核 → OCR COST”。
5. 实时预检确认存在但正式装备阶段未找到，视为页面或识别状态异常；本地库模式下正式
   定位未找到则视为库存记录过期或满破未知，排除该 ID 后重新规划。两者都不得误点
   相似卡面。
6. COST 不足时先换用更低 COST 的次优礼装；仍不满足则卸下本 Action 新增、边际收益
   最低的礼装并重新规划。没有正收益、没有空位或所有组合均无法满足 COST 时停止；
   不为了填满格位选择无羁绊效果礼装。

### 阶段 D：最终验证

最终从新截图重建实际状态，并进行三项检查：

1. COST OCR 合法且 `used <= max`；
2. 每个保护槽和选项锁定槽仍符合初始状态，新增对象均位于允许空位或可替换位置；
3. 用实际识别到的从者、礼装、变体和 COST 重新计算 `team_score`。若与最终计划不一致，
   不点击决定；若一致，记录“基线分 → 最终分、增量、剩余 COST、未找到对象”。

在实时扫描确认拥有或本地库声明持有的候选集合内，再跑一次同样的组合搜索；若存在满足 COST
且更高分的替换，只允许替换本 Action 自己新放入的对象并复核。这样“最大化”的定义是
**当前可信候选池内的最优解**。本地文件 `catalog_complete=false` 或实际库存自生成后
发生变化时，结果不宣称是玩家当前全仓的数学全局最优；Focus 和普通日志必须说明实际
采用“本地快速”还是“实时扫描”模式。

## 7. 安全失败与日志

问题按“可恢复”和“不可确认”两级处理；日志和任务结果必须给出明确原因，不能只输出
“补齐失败”：

- 可恢复：某个候选不存在、COST 不足但可降级、个别候选缺资源、没有更优组合。排除或
  回退该候选后继续；最终状态可完整复核时，提交安全的部分结果并将任务记为成功，同时
  输出 `bond_completion_partial` 或 `bond_completion_no_change` 及具体原因。
- 不可确认：连续 COST OCR 失败、保护槽变化、页面状态未知、选择后无法确定实际对象。
  停止点击并尝试退出本次编辑、恢复第一阶段已经确认的 Chaldea 队伍。恢复且复核成功时
  任务记为“成功但未补齐”，输出 `bond_completion_aborted_safe`；无法恢复或无法复核时
  整体任务失败，并输出下表中的精确错误码。

| 错误码 | 条件 |
| --- | --- |
| `bond_completion_cost_ocr_failed` | COST OCR 缺失、格式非法或前后矛盾。 |
| `bond_completion_cost_exceeded` | 预估或实测 COST 超限。 |
| `bond_completion_slot_invalid` | 助战/保护槽/空槽识别不可信。 |
| `bond_completion_resource_missing` | 计划对象缺少必要图片或 COST/特性资料。 |
| `bond_completion_select_verify_failed` | 选从者/礼装后未返回或模板复核失败。 |
| `bond_completion_equip_preflight_failed` | 礼装库存预检的筛选、回顶、扫描或返回状态异常；不代表库存没有。 |
| `bond_completion_final_mismatch` | 保护规则、COST 或评分复算不一致。 |
| `bond_completion_restore_failed` | 中止补齐后无法确认已恢复第一阶段队伍。 |

日志至少输出：原 Chaldea 本地槽、可补槽、COST OCR 原文及数值、优先星级队列、每个
候选的拒绝原因、已确认礼装、基线/最终羁绊分、每名从者的命中特性和贡献、最终剩余
COST。不得记录或上传用户的分享链接内容。

## 8. 验收场景

- 开关关闭：原自动编队行为、点击次数和结果完全不变。
- Chaldea 恰好五名本地从者：不补人，只在允许空礼装位补入有收益礼装。
- 仅三名本地从者、一个助战：只填两个真实 `SELECT` 空位，不覆盖任何既有成员。
- Chaldea 仅指定三名本地从者、另外两槽残留旧从者：从者选项为“否”时识别、锁定并
  纳入评分；为“是”时允许逐槽替换，并按新旧 COST 差复核。
- 其他位置已有礼装：礼装选项为“否”时不点击该槽并在最终做截图一致性复核；为“是”
  时首次规划前卸下、读取释放后的 COST，再参与全队礼装重算。
- 优先 3 星、3 星完整扫描没有命中：复位后按 `3,5,4,2,1,0` 顺序切换筛选并扫描。
- 本地从者库有效：不执行星级持有收集扫描，直接规划并回顶定位最终从者；从者文件无效
  时仅从者类别回退实时扫描，礼装模式不受影响。
- 本地礼装库有效：候选严格限制在文件 ID 中，不执行礼装库存预检；礼装文件无效时仅
  礼装类别回退实时预检，从者模式不受影响。
- 本地库记录目标已不存在，或礼装只有非满破版本：排除该 ID 并重新规划，不误点其他
  对象；从者目标缺失时复用同一轮完整查找结果批量刷新该星级候选，不能逐个候选重扫；
  筛选或页面状态异常仍安全中止。
- 同一星级多名从者均存在：完整下滑扫描至多 15 次后，再计算唯一最优者；复位列表后
  只选择该对象，不会先点到其他候选。
- 当前最优从者超 COST：先尝试同星级更低 COST 候选，再按星级顺序尝试更低 COST 从者。
- 新增礼装导致 COST 不足：换低 COST 礼装；仍不足时只卸下本功能新增的最低收益礼装。
- Chaldea 已指定礼装、自动编成礼装关闭：该礼装槽仍不得被新功能点击。
- 最优礼装在数据库存在但仓库不存在：标记 unavailable、重新规划其他礼装并继续。
- 某从者的预计优势依赖玩家没有的礼装：在点击从者前排除该礼装，并重新计算从者与礼装
  联合优先级；不得先选从者再只更换礼装。
- 礼装预检存在、正式装备却未找到：按识别异常停止并保留当时画面，不标记库存缺失。
- 活动限定羁绊礼装：归档信息可见，但默认不进入常驻候选。
- OCR 读成非 `XX/XXX`：安全停止，不按预测 COST 继续。
- 个别礼装实际缺少 list/team 模板：跳过并明确输出礼装 ID 与缺失路径，不误点仓库首项。

## 9. 已确认的实施决定

1. 接受原编队确认后重新进入配置页、补齐后再次确认的两阶段流程。
2. 优先星级默认 5 星。
3. `bond_base` 默认 1200，同时提供可修改的正整数输入项。
4. 补从者时 COST 不足则换更低 COST 从者；补礼装时换低 COST 礼装，必要时卸下本功能
   新增的最低收益礼装。
5. 允许给当前没有 Chaldea 指定礼装的本地从者空礼装位补装；已指定位置保持现状。
6. 每种礼装最多选一张，不考虑多副本。
7. 复用现有编队礼装模板库，不新增一套重复模板。
8. 可安全复核时保留部分成果并成功返回；只有状态无法恢复或无法确认时失败，所有问题
   都通过明确状态码、对象 ID、槽位和原因报告。
9. “自动修改其他位置从者”和“自动修改其他位置礼装”默认均为“是”；选择“否”只锁定
   Chaldea 未指定位置上已经存在的对象，真正的空从者位/空礼装位仍按补齐规则处理。
10. 礼装库存采用按需预检；缺失礼装会在任何对象落地前触发当前从者与礼装联合重规划，
    而不是只在最终装备阶段换下一张礼装。
11. 本地从者库与本地礼装库分别提供独立开关，默认均为“否”；任一文件无效只回退该
    类别的实时扫描，不影响另一类别使用快速模式。
12. 快速模式只使用 schema v1 完整扫描文件中的可靠 ID；业务属性仍取工程目录。本地
    礼装库不能证明满破，正式定位失败时排除并重规划。
