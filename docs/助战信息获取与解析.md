# FGO 助战（followerlist）信息获取与解析

> 2026-08-07 实测整理（2026-08-08 更新：显示条目选择与排序规则改为**代码级结论**，依据日服 APK 解包 `dump.cs` + `libil2cpp.so` AArch64 反汇编）。目标：从模拟器内 Reqable 的抓包中，外部程序（宿主机）按需拉取指定关卡进入时的助战列表，并解析出玩家名 / 从者 / 技能 / 宝具 / 追加被动 / 礼装等中文可读信息。
> 已验证样本：questId=93040211（第 3 阶段，非活动关卡），28 名玩家 / 480 条从者条目；ALL 阶显示条目 40 条（好友 27 + 非好友 13），排序与屏幕一致。

## 1. 访问 Reqable 抓包数据

Reqable（模拟器内，`com.reqable.android`，API 端口与代理端口相同）监听 `0.0.0.0:9000`，宿主机经 adb 端口转发访问：

```powershell
# 转发（每次重启模拟器/Reqable 后需重做）
adb -s 127.0.0.1:16416 forward tcp:9000 tcp:9000
```

### 1.1 定位助战记录

```powershell
# 全部记录 ID（按需过滤，见下）
curl.exe -s -m 15 -X POST http://127.0.0.1:9000/capture/live/filter `
  -H "Content-Type: application/json" -d '{\"filters\": []}'
```

更精确：用 filter 按 URL 关键字过滤 `followerlist`（Reqable filter 支持 url/keyword/host/method 等类型，可多条件 AND）。

### 1.2 取记录详情

```powershell
curl.exe -s -m 20 -X POST http://127.0.0.1:9000/capture/live/get `
  -H "Content-Type: application/json" -d '{\"id\": 312}'
```

### 1.3 响应体临时文件（关键坑）

助战响应**很大（1MB+ base64）**，Reqable 不直接给内容，`response.body.text` 只给临时文件路径：

```
/data/user/0/com.reqable.android/files/tmp/<uuid>
```

需 adb 拉回再解码：

```powershell
adb -s 127.0.0.1:16416 shell "cat /data/user/0/com.reqable.android/files/tmp/<uuid>" > raw.txt
```

### 1.4 解码链路

```
URL 解码(UnescapeDataString) → base64 解码 → JSON
```

注意：base64 末尾 `==` 有时被 URL 编码成 `%3D%3D`，PowerShell 直接 `FromBase64String` 会报"非有效 Base-64"，必须先 `[System.Uri]::UnescapeDataString()`。

```powershell
$raw = [IO.File]::ReadAllText('raw.txt')
$clean = [System.Uri]::UnescapeDataString($raw) -replace '\s',''
$json = [Text.Encoding]::UTF8.GetString([Convert]::FromBase64String($clean))
```

## 3. 响应结构（服务端 → 客户端）

解码后的 JSON：

```
response[0].nid = "follower_list"
response[0].isEncrypt = 0
cache.updated.userFollower[0].followerInfo[]   ← 助战条目数组（顺序即服务端下发顺序）
cache.updated.serverTime
```

> ✅ 2026-08-08 实测（国服 B 服，Reqable 抓包）：`battlesetup`/`battleresume`/`followerlist`/`home`/`toplogin`（ac.php 全系）及 `member.php`/`login.php` 响应**全部 `isEncrypt=0`**，统一解码链路 = URL 解码 → base64 → JSON，**无需真正解密**。`battlesetup`（nid=`battle_setup`）响应实测：`success={}`，含 `questIds[]`（服务器下发关卡列表）+ **`cache.replaced.battle`（战斗核心数据，详见 §3.4）** + `cache.updated.userQuest`（questId/questPhase/status=16）+ `userGame`；响应头 `encryptApi=['battlesetup','battleresume']` 仅为"支持加密"声明，本次未启用（若未来某次返回 `isEncrypt=1`，success 段才可能加密，可参考 chaldea-main 的 `lib/app/modules/tools/cipher_test.dart` 手动解密工具：Base64 / msgpack / DES3 / Rijndael）。

### 数据层级（重要）

`followerInfo` 的条数是**玩家数**，不是从者条数。实测 questId=93040211 一次响应：

```
28 名玩家（followerInfo 条目）
 └─ 每个玩家 1~3 套支援卡组（supportDeckId，由 mainSupportDeckIds 区分）
     └─ 每套卡组 9 个职阶槽位（classId 0~8，可空）
         └─ 每个槽位 = 一条从者条目（userSvtLeaderHash 元素，含技能/宝具/被动/礼装）
```

| 统计项 | 数值 |
|---|---|
| 玩家数 | 28 |
| 从者条目总数 | 480 |
| 每玩家条目数 | 9（1 套卡组）~ 27（3 套卡组） |
| 每玩家 class-0(ALL) 候选 | = 卡组数（1~3 条） |

即：**一个玩家在多个职阶都有助战信息**，按 `(supportDeckId, classId)` 铺开在数组里。**客户端按 玩家×卡组 生成显示条目**：某 tab（如 ALL 阶）显示每名玩家**每套卡组的对应槽位各 1 条**（ALL=每卡组 class-0 槽位）。实测 stumm / 喷喷喷不动了 / 顺手捞只湘皮皮团 各出现 3 条（3 套卡组）。全量 480 条都在一次响应里，切职阶 tab 无需再发请求。

### 3.4 进入关卡（battlesetup）响应结构

> ✅ 2026-08-08 实测（questId=94147015）：战斗数据**全部在 `cache.replaced.battle` 下，不在 `success`**；`success={}` 说明该次为复战/续战（关卡已解锁），若首次进入 success 段才可能携带数据。

```
response[0].nid = "battle_setup"
response[0].success / fail          ← 本次为空 {}
response[0].questIds[]              ← 服务器下发关卡列表（预加载用，非本次进入关卡）
cache.replaced.battle               ← 战斗核心数据（关卡参数 + 双方卡组 + 从者详情）
cache.updated.userQuest / userGame  ← 关卡状态 / 账号数据
```

| 字段 | 说明 |
|---|---|
| `questId` / `questPhase` | 本次进入的关卡 ID / 阶段 |

| `deckNo` | 我方出阵卡组号（字符串，如 `"4"`） |

| `followerSupportDeckId` / `followerClassId` | 助战所取卡组 / 职阶槽位（0=ALL） |
| `resultInfo` | 通关奖励：`rewardQp` / `rewardExp` / `rewardFriendPoint` / `rewardFriendShipDic{svtId→羁绊点}` |

#### 3.4.2 battle.battleInfo 字段（双方卡组与从者详情）

| 字段 | 说明 |
|---|---|
| `myDeck.svts[]` | 我方出阵顺序：`{userSvtId, userSvtEquipIds[], deckPos, isFollowerSvt(是否助战)}` |
| `enemyDeck[]` | 敌方**按波次**的卡组数组，每波 `{svts[]}`，元素含 `name`（如 巨蛇A）/ `npcId` / `deckSvtName` / `roleType` / `dropInfos[]` |

## 4. 显示条目选择规则（代码级，日服解包确认）

每个玩家有 1~3 套支援卡组（`supportDeckId` 区分，`mainSupportDeckIds` 列出），每套 9 个职阶槽位。**客户端为每个玩家的每套卡组各生成一条列表条目**（`FollowerSelectItemListViewManager.CreateList`），屏幕上某 tab（如"ALL 阶"）显示每玩家每卡组对应槽位各 1 条：

> 显示条目 = 对每个玩家遍历其卡组，每个 `mainSupportDeckIds` 中卡组的 **class-0 槽位**（ALL）生成一条（槽位有值才显示）。

## 5. 排序规则（客户端行为，代码级）

游戏内支援列表排序由客户端**本地执行**（与响应下发顺序无关）。依据日服 APK 解包（`dump.cs`）+ `libil2cpp.so` AArch64 反汇编（`FollowerSelectItemListViewManager.SetSortValue` @0x256A798、`ListViewItem.SortCompUp/Down` @0x30621A4/@0x306228C）：

- 排序配置 = `ListViewSort{ sortKind(排序方式), priorityKind(概念礼装的优先), isAscendingOrder(升降序) }`，三者独立、共同决定最终顺序
- `ListViewManager.SortItem`（RVA 0x3065138）按 `sort.isAscendingOrder` 选比较器：false → **`SortCompDown`**（RVA 0x306228C，8 键全**降序**）；true → **`SortCompUp`**（RVA 0x30621A4，仅 `sortValue1/1B` **升序**，其余 6 键仍降序）
- 比较器链式比较 8 个排序键，逐个比大小，全部相等返回 0（保持稳定插入序）
- **结论：28 种组合（7 优先 × 4 排序方式）共用同一条 8 键比较链，差异只在 sortValue0 与 sortValue1 的取值**，见 §5.3/§5.4

### 5.1 排序键（`ListViewItem` 字段，由 `FollowerSelectItemListViewItem.SetSortValue` 填充）

| 偏移 | 键 | 取值（助战列表语境） |
|---|---|---|
| +0x20 | sortValue0 | **概念礼装优先值**（§5.3）；不优先=0；NPC=1e12（`SORT_VALUE_NPC`，恒排最后） |
| +0x28 | sortValue0B | **type 标记**：FRIEND=3 / NOT_FRIEND=2 / FOLLOW=4（排序方式为登录顺序时用 5/4，相对大小不变）；另含 ±10/100 偏移位（对所有条目一致，不改变组内顺序） |
| +0x30 | sortValue1 | **排序方式键**（§5.4）：登录时间戳 / 从者等级 / HP+ATK / ATK |
| +0x38 | sortStr1 | 字符串键（助战列表为空） |
| +0x40 | sortValue1B | 0 |
| +0x48 | sortValue2 | 平局键（SortCompDown 全降序）：`classIndex > 0 ? classIndex : 从者图鉴编号 collectionNo`（@0x256AFD8；助战列表 classIndex 未设置→走 collectionNo） |
| +0x50 | sortValue2B | 仅登录顺序=deckPriority(卡组优先级 @0x256A968)；其余排序方式恒 0 |
| +0x58 | sortValueLast | 0 |

### 5.2 实际排序效果（可观测键）

```
sortValue0(优先效果值/NPC) → sortValue0B(好友3 > 非好友2) → sortValue1(排序方式键)
→ sortStr1 → sortValue1B → sortValue2(classIndex/collectionNo) → sortValue2B → sortValueLast
```

即屏幕上：**概念礼装优先值大的在前 → 好友全部排在非好友之前 → 组内按排序方式键**；平局按 sortValue2（等级顺序=图鉴编号 collectionNo 降序，客户端 @0x256AFD8：`classIndex>0?classIndex:collectionNo`）→ sortValue2B（仅登录顺序=deckPriority，其余恒 0）；全等保持响应插入序。

> ✅ 2026-08-07 屏幕对照验证：120 级平局组按 collectionNo 降序 = Phantasmoon(431) → C.I.E.L(418) → 埃列什基伽勒(417) → 岩窟王(96)，与屏幕完全一致；早期用 supportDeckId 近似 deckPriority 是错的（supportDeckId=+0x110 不参与排序）。
>
> ✅ 2026-08-08 代码级定稿：标准助战列表 `classIndex` 恒 0（非待验证），sortValue2 恒=collectionNo。`SetClassId`(RVA 0x2578444) 按 `IsMixSupportGroupType`(0x2D947B8，`classPos==9`)/`IsRecommendSupportGroupType`(0x2D947C4，`classPos==10`) 三选一列表源：标准助战列表 classPos 0-8（`SupportGroupType` 枚举 ALL=0..EXTRA=8）一律用 `originalItemList`(+0x210)，其条目仅由 CreateList 内 0x257612C/0x2576668 两个 ctor 调用构造且均 `mov w2, wzr`(index2=0)→classIndex(+0x10C)=0；只有 MIX(9)/RECOMMEND(10) 特殊 tab 才用含倒计实例（classIndex=supportDeckMemberMax-索引>0）的 `mixItemList`(+0x208)/`recommendItemList`(+0x218)。
>
> ✅ 2026-08-08 代码级定稿：type5(FOLLOW) 在列表构建阶段即被过滤，不参与排序。`CreateList` 外层循环（逐 FollowerInfo）@0x25764D0~0x2576504：`ldr w8,[x25,#0x24]`(FollowerInfo.type=+0x24) → `cmp w8,#5`；普通关卡（`QuestEntity.HasFlag(0x8000000)` @0x2F24758 返回 false）`b.eq #0x2576a68` 无条件跳过该条目；有该 flag 的关卡则 type==5 时经 `IsFollowUser(userId)`(@0x2FB7A20) 检查，非关注用户同样跳过。故 FOLLOW 条目从不进入 originalItemList 参与排序，sortValue0B 的 FOLLOW=4 分支不产生实际排序效果。

### 5.3 概念礼装的优先（`priorityKind` → sortValue0）

`CalculatePriorityKindSortValue`（@0x256A530）计算礼装是否带对应效果并按效果强度编码（2026-08-07 实抓屏幕对照验证）：

```
sortValue0 = 主项 + (礼装hp + 礼装atk) × 10 + (limitCount ≥ 阈值 ? 1 : 0)
主项 = 档位 × 条件数
  档位 = RateCount/100 取整：1(10%)→×100000、2(20%)→×100000000、其他→主项0
  条件数 = functvals 元素数 + overwriteTvals 内层特性总数（无条件礼装=0）
不含对应效果的礼装 → 0（如黑之圣杯无羁绊效果，牵绊提升下=0）
```

> 例（牵绊提升）：检查报告 20%〔秩序且善〕(overwriteTvals 2 特性) = 2档×2=2e8；
> 迦勒底之晨/ＮＦＦ的爱 20%〔1 特性〕 = 2档×1=1e8；午餐时光 10% 无条件 = 1档×0=0；
> 同礼装不同等级按 (hp+atk)×10 微调（如检查报告 lv19 > lv15）。
> `GetValuesDictionary`（@0x256A0E8）按 `priorityKind` 在礼装技能效果（`FuncList.TYPE`）中匹配：

| 优先选项 | PriorityKind | 匹配效果 TYPE | 说明 |
|---|---|---|---|
| 不优先显示 | NONE=0 | — | sortValue0 恒为 0，不参与区分 |
| 友情点提升 | FRIEND_POINT_UP=1 | 104 `FRIEND_POINT_UP` / 123 `FRIEND_POINT_UP_DUPLICATE` | 含友情点加成礼装优先 |
| 御主经验提升 | MASTER_EXP_UP=2 | 101 `EXP_UP` | |
| 魔术礼装经验提升 | EQUIP_EXP_UP=3 | 112 `USER_EQUIP_EXP_UP` | |
| 牵绊提升 | BOND_UP=4 | 111 `SERVANT_FRIENDSHIP_UP` | 午茶/下午茶等羁绊礼装 |
| QP提升 | QP_UP=5 | 102 `QP_UP` / 110 `QP_DROP_UP` | |
| 掉落提升 | DROP_UP=6 | 106 `EVENT_DROP_RATE_UP` | 注意：不含 103 `DROP_UP` / 105 `EVENT_DROP_UP` |

> 主效果数值按 §5.3 公式由效果强度档位×条件数得到；礼装有多个匹配技能时取最大值（遍历分支见 SetSortValue）。

### 5.4 排序方式（`sortKind` → sortValue1）

| 排序方式 | SortKind | sortValue1 | 降序效果 |

### 5.5 7×4 组合规则（28 种，统一公式）

# ---- 概念礼装优先 → sortValue0（客户端 0x256a530 CalculatePriorityKindSortValue）----
function Get-PriorityValue($equip) {
    if ($Priority -eq 0 -or $null -eq $equip -or [long]$equip.svtId -le 0) { return [long]0 }
    $sid = [string]$equip.skillId1
    $rate = 0; $cond = 0; $found = $false
    switch ($Priority) {
        4 { if ($bondRate.ContainsKey($sid)) { $r = $bondRate[$sid]; $rate = $r[0]; $cond = $r[1]; $found = $true } }
        5 { if ($qpRate.ContainsKey($sid)) { $r = $qpRate[$sid]; $rate = $r[0]; $cond = $r[1]; $found = $true } }
    }
    if (-not $found) { return [long]0 }
    $lvl = [int]($rate / 100)
    $main = 0L
    if ($lvl -eq 1) { $main = 100000L * $cond }          # 10% → 档位1
    elseif ($lvl -eq 2) { $main = 100000000L * $cond }   # 20% → 档位2
    $sub = ([int]$equip.hp + [int]$equip.atk) * 10
    $bit = 0
    if ([int]$equip.limitCount -ge 1) { $bit = 1 }       # limitCount 阈值未知，满破礼装 bit 相同
    return ($main + $sub + $bit)
}
